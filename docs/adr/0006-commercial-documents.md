# ADR-0006 · Commercial documents: quotations and invoices

Status: accepted (Phase C, `docs/ADDITIONAL-REQUIREMENTS.md`; owner decisions 5 and 6, 23 Oct 2026). Extends booklet ch. 13.6 (quotes), 13.7 (payments), 14.9 / 24 (documents), 17 (notifications), 27.6 (ATOL timing). Ch. 35.1 rule 10: the booklet has no invoice object, so this records the addition.

## Decisions

| # | Question | Decision | Why |
|---|---|---|---|
| C1 | Quotation | Not a new object. A **quotation is the sent quote** plus a document number (`QT-2026-000001`), a PDF (`documents`, type `QUOTE_PDF`) and an email. The number is allocated in the transaction that sends the quote and printed on the PDF | Rule 3 of ch. 35.1: quote, offer snapshot, reservation, ticket and payment stay separate objects; a second "quotation" table would duplicate the quote |
| C2 | Invoice | New aggregate: `invoices` (+ `invoice_lines`, insert-only `invoice_status_history`). An invoice is built **by the server from the accepted quote option** (flight: fare, taxes and carrier charges, service fee; cargo: the accepted quote's lines). Staff never type an amount | Amounts cannot drift from the accepted quote; ch. 13.6 "a price change after acceptance needs a new quote" |
| C3 | States | `DRAFT → ISSUED → PAID | CANCELLED`, `PAID → REFUNDED`. **Expiry is not a state**: an ISSUED invoice whose `expiresAt` has passed moves to `CANCELLED` with reason code `EXPIRED` (system actor). Staff cancellations carry `STAFF_CANCELLED` or a staff reason code | Fewer states for every client to render and test; the reason code keeps the two cases distinguishable (separate notification templates `invoice.expired` / `invoice.cancelled`, separate customer wording). A distinct state would add no transition the machine does not already have |
| C4 | Amounts fixed at issue | Lines and totals are writable only while `DRAFT`. A database trigger refuses any change to `total_minor`, `currency`, `number` on a non-draft invoice and any insert, update or delete of its lines. Corrections are **cancel + reissue** (the new invoice gets a new number; the old one stays, CANCELLED) | Rule 3 truth model; an invoice number never means two different amounts |
| C5 | PAY_ON_TICKETING guard | Under `atolMode = PAY_ON_TICKETING` a **flight** invoice can be issued only when the request is `TICKETED`/`COMPLETED` and the tickets were recorded on **the same Europe/London calendar day** as the issue. It then expires at **the end of that day** (the next 00:00 Europe/London, DST-aware). Other ATOL modes and cargo: expiry is issue time + `invoiceValidityDays` (config, default 14) | Ch. 27.6: money is taken only together with tickets, so a payable document before ticketing would invite a deposit. "Day" is Europe/London because the booklet's business hours are defined in Europe/London and Asia/Tehran (ch. 13.5) and the seller is UK-based. INFERRED: the booklet does not define "same-day"; needs counsel/accountant confirmation |
| C6 | Numbering | `document_sequences(kind, year)` with `last_value`. The number is `PREFIX-YYYY-NNNNNN`; prefixes (`quotePrefix`, `invoicePrefix`) are configuration (`AppSettings.commercialDocuments`). Allocation is `INSERT .. ON CONFLICT DO UPDATE SET last_value = last_value + 1 RETURNING` **inside the issuing transaction**: the row lock serialises concurrent issuers and a rollback releases the number, so the sequence is gap-free and concurrency-safe. The year is the Europe/London year of issue | A Postgres `SEQUENCE` would burn numbers on rollback (gaps) |
| C7 | Company particulars | Registration number, VAT number, VAT treatment and registered address are configuration values, all `null` (UNKNOWN) by default (decision 5). The PDF prints "UNKNOWN - to be confirmed by the accountant" in place of each unset value. Nothing is invented. Issuing is not blocked locally | Owner decision 5 and rule 7 |
| C8 | Delivery | Through the notification system (ch. 17), event types `quotation.sent`, `invoice.issued`, `invoice.cancelled`, `invoice.expired` (en/fa templates, seeded). Email goes to the **verified email**; the body carries a **short link** (`short_links`) to the document page, which redirects to the web app and requires sign-in. The PDF is **not attached**: an amount in a mailbox is outside our access control. Without a verified email the same event goes by **SMS and in-app** (decision 6). These events always include INBOX and EMAIL regardless of the stored matrix, so databases created before this phase need no matrix migration | Decision 6; ADR-0004 (amounts only behind sign-in) |
| C9 | Visibility | A customer sees amounts only on a **sent quote** and an **issued invoice** (any non-DRAFT state, so CANCELLED/PAID/REFUNDED stay readable). `DRAFT` is invisible (404). The billing list carries no quote amounts (the quote itself is on the request page). Staff see amounts only with `pricing.read.internal`; downloading the priced PDF types (`QUOTE_PDF`, `INVOICE`) as staff needs it too | ADR-0004 |
| C10 | Permissions | None new. Create draft, issue, cancel: `commercial_document.issue` (admin, owner). Read the staff list/history: any of `flight_request.read.any`, `cargo_request.read.any`, `commercial_document.issue`. Amounts in those responses: `pricing.read.internal`. Customer routes: `flight_request.read.own`/`cargo_request.read.own`-style authenticated routes with ownership checks (404 for others) | ADR-0004 table |
| C11 | Payment seam (Phase D) | The domain exposes `mark_paid` and `mark_refunded` (SYSTEM actor) and `InvoicesService.markPaid(tx, invoiceId, paymentRef)` / `settleFromPayments(tx, requestType, requestId)`. Offline payment recording (including the four-eyes verification) calls `settleFromPayments`; Phase D's verified Stripe webhook calls `markPaid` with its payment record. No online-payment code is added here | Out of scope per the phase brief |
| C12 | Expiry job | A delayed BullMQ job per ISSUED invoice (`inv-<id>--invoice.expire`, `:` is not allowed in BullMQ ids) through `TimersService`, rebuilt by its reconcile, plus a `maintenance` repeatable `invoices.expire-due` every 5 minutes that expires anything overdue. The domain guard (`now >= expiresAt`) is re-checked when the job fires | The database is the source of truth, as for SLA timers |

## Consequences
- Customers get a "Documents & billing" area (web `/billing`, Flutter equivalent); staff get invoices on the request page and an Admin Panel list.
- The email vendor is unchanged (`EmailSender`, Mailpit locally, Brevo listed but not contracted), so the DPIA vendor table is unchanged; processing now includes invoice data (document numbers, links) in notification rows.
- The accountant's answers (registration, VAT, numbering format) replace configuration values, not code.
- UNKNOWN: whether VAT applies to the service fee and to which supplies; the PDF shows no VAT lines until `vatTreatment` is set.
