# ADR-0013 · Staff amendments, discount and extra-service lines, payment emails

Status: accepted (27 Oct 2026, owner request "complete Stripe payment, booking request, invoice and email integration"; scope chosen by the owner after the audit: traveller edit fix, payment emails, discounts and extras, staff edit of trip details; Stripe test keys not yet available). Extends ADR-0006 (commercial documents) and ADR-0007 (Stripe). Ch. 35.1 rule 10: each item below adds to or interprets the booklet where it is silent.

The owner's brief also asked for things this ADR keeps out because earlier decisions already answer them: live card payments (ADR-0007 P1, BLOCKED on Stripe's approval and counsel), staff typing invoice amounts (ADR-0006 C2), PDFs or amounts attached to emails (ADR-0006 C8, ADR-0004) and payment links that work without signing in (ADR-0007 P17). Those decisions stand.

## Decisions

| # | Question | Decision | Why |
|---|---|---|---|
| A1 | Staff edit of a request's trip | New staff action **amend** (`POST /v1/admin/flight-requests/:ref/amend`, permission `flight_request.transition`). It replaces the request's `query` (trip type, slices, cabin, passengers) and/or its travellers, with a mandatory reason (5+ characters) and the request's `expectedVersion`. It is **not** a state transition: the status does not change | The booklet has no amendment before booking; after-sales (ch. 13.8) covers changes after ticketing. Customers phone in changes, and today staff can only express them inside a quote |
| A2 | When amend is allowed | `NEW`, `IN_REVIEW`, `AWAITING_CUSTOMER`, `QUOTED`, `ACCEPTED` (domain `amendAllowed`). From `RESERVED` on, the PNR is the truth and changes go through after-sales. In `QUOTED`/`ACCEPTED` staff must confirm `acknowledgeOpenQuote: true`: the sent or accepted quote still describes what it described (rule 3; a quote is never rewritten) and staff send a new quote, which supersedes it (ADR-0003) | A quote is what the customer accepts; amending the ask must not change an offer silently |
| A3 | What is kept | Insert-only `request_amendments` (request, version before, actor, reason, `before` and `after` JSON of the changed fields). The staff timeline shows each amendment with its reason; the customer timeline shows "Details updated by Uni Travel" and the request page shows the current details. Audit action `flight_request.amended` (before/after) and a customer notification `request.amended` | Prompt asks for previous and updated values; audit trail for every staff change |
| A4 | Checks on amended data | Same rules as submission: the query passes `SearchQuery`; travellers must belong to the customer; the per-type traveller mix must equal the query passengers (ADR-0008 W6). **Compliance is never skipped (rule 5):** every traveller not already on the request is screened, and the new route's countries go through the route policy. Any hit **refuses the amendment** (`COMPLIANCE_HOLD`), opens a compliance case with the evidence, and leaves the request unchanged; a status change into hold from these states is not in the state table, so refusing is the conservative choice | Rule 5; ch. 27.1 |
| A5 | Discount and extra-service lines | A flight quote option's `priceBreakdown` gains optional `extras: [{ label, amount }]` (up to 10, each > 0) and optional `discount: { label, amount }` (> 0, at most the sum of the other parts). The **total is computed by the domain** (`priceBreakdownTotal`: fare + taxes + service fee + extras − discount) and the server refuses a total that differs, a non-positive total, or a mixed currency. Discounts need no new permission: whoever may price a quote (`pricing.write`, admin and owner) may discount it | Rule 3: amounts are server-authoritative. No schema change: `priceBreakdown` is JSON. Cargo quotes keep their own line model |
| A6 | Invoice lines | The invoice built from an accepted option gets one line per extra and a **negative** line `Discount - <label>` (invoice lines have no sign constraint; the total check stays `> 0`). The quotation PDF and the customer request page show the extras and the discount | ADR-0006 C2 (the server builds the invoice from the accepted option) |
| A7 | Payment emails | New events, all sent as documents (INBOX + EMAIL to the verified email, SMS when no verified email; ADR-0006 C8), **without amounts** (ADR-0004): `invoice.paid` (emitted by `InvoicesService.markPaid`, so card and verified offline payments alike, once per invoice by the state machine), `payment.failed` (an asynchronous card payment failed; the invoice stays payable), `payment.refunded` (each time the provider reports a larger refunded amount), `payment.requested` (the staff "resend payment link" action; replaces the re-sent `invoice.issued`) | ADR-0007 P18 left receipts and refund messages UNKNOWN; the owner asked for them. Each is emitted inside the transaction that records the state change, which is itself deduplicated (`stripe_events`, `provider_ref`, the invoice machine), so a repeated webhook cannot send twice |
| A8 | Expired checkout sessions | No customer message. A Stripe session expiring is not the invoice expiring (`invoice.expired` already exists); the customer can open the Pay page again | Avoid noise |
| A9 | Traveller PATCH | `PATCH /v1/me/travellers/:id` used `TravellerInput.partial()`, and Zod 4 keeps `.default("SELF")` inside `.partial()`, so a patch without `relationship` turned the traveller into SELF (or failed when a SELF existed). New `TravellerPatch` with no defaults | Bug found in the audit |

## Consequences
- Migration `0009_request_amendments` (insert-only table, grants like `request_status_history`). No new permission, so no `perm_version` bump.
- Event catalogue and default matrix gain `request.amended`, `invoice.paid`, `payment.failed`, `payment.refunded`, `payment.requested`; seeded en/fa templates. Databases seeded earlier get the templates from `pnpm db:seed` (idempotent) and the channels from the document-delivery rule, so no matrix migration.
- Console: amend dialog on the request page, extras and discount rows in the quote builder.
- UNKNOWN: whether a discount changes the VAT treatment (ADR-0006: no VAT lines until `vatTreatment` is set).
