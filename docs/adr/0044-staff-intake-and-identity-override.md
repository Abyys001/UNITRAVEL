# ADR-0044 · Staff create requests for customers; tickets without identity verification

Status: accepted (owner instruction, 19 Nov 2026: "do this on all the system: admin can create ticket without the verification; for cargo let the admin create cargo, admin issue ticket"). Amends ADR-0005 owner decision 4 (VERIFIED documents required at `record_tickets`) and ch. 11.3 / 14.3 (verified contact phone) for **staff** actions only. Customers' own submissions keep every existing check.

## Decision

1. **Staff intake everywhere.** Staff create requests on a customer's behalf for all products: cargo (ADR-0042 D13, `cargo_request.create.any`), flights (new, `flight_request.create.any`, admin and owner; `POST /v1/admin/intake/flight-requests`, console Requests › New request) and services (ADR-0020 admin-assigned services). The customer is found by an exact email, phone or `UT-` reference (`GET /v1/admin/intake/customers`, audited, rate-limited, never a browse; staff accounts are never customers) or created from a name and email (customer role only).
2. **Nothing has to be verified to submit.** For staff intake the contact phone may be unverified (an unverified phone identity is added when the customer has none), travellers are created on the customer's account as given (passport optional, verification UNVERIFIED), and the request records `created_by_staff_id` and `intake_channel`; submission is audited as `*.submitted_by_staff`, travellers as `traveller.created_by_staff`. Staff-created flight requests are MANUAL (staff build the options). Staff confirm the customer agreed (`customerConfirmed`).
3. **Ticketing without identity verification.** `record_tickets` no longer hides behind unverified travellers: staff with `ticket.record` may record tickets for travellers whose document is not VERIFIED by giving a reason (≥ 10 characters). The reason, the staff member and the time are stored on the request (`identity_override_*`), audited as `flight_request.identity_override` with the travellers' statuses, and shown on the request page. Without a reason the API still answers 409 `IDENTITY_NOT_VERIFIED` (now with `overrideAllowed: true`). The domain guard moved from the state guard to the input guard so the command stays offered; the property test asserts TICKETED implies verified travellers **or** a recorded reason. The traveller's verification state itself is not changed.
4. **Continue without the customer (owner, 19 Nov 2026: "let the admin approve and move to the next").** Flights and cargo get the staff command `resume_review` (AWAITING_CUSTOMER → IN_REVIEW, `flight_request.transition` / `cargo_request.transition`) with a required note (e.g. "answered by phone"), stored as the history reason and an internal note. Every other customer step already has a staff equivalent (record acceptance for quotes; services: record acceptance, complete, cancel).
5. **Add a price straight away (owner, 19 Nov 2026: "the admin should be able to add the price").** Drafting a quote (flights and cargo) on a NEW request claims it for the staff member, and on an AWAITING_CUSTOMER request runs `resume_review` ("Staff prepared a quote") first — ordinary audited transitions. Screening states (SUBMITTED, COMPLIANCE_HOLD) stay locked. The console shows "Add price / quote" from NEW onwards, on mobile too. Unknown baggage or fare conditions still block sending (rule 3).
6. **Never bypassed.** Sanctions/party screening of travellers, goods, lanes and parties, the state machines, payment rules (PAID or owner-approved credit override, ATOL mode, four-eyes) and every other compliance policy apply unchanged (rule 5).

## Consequences

- A request can be ticketed for a traveller nobody verified; the stored reason is the control, and the audit log shows who used it. Compliance can review overrides by the audit action.
- New customers created by staff receive notices only after they sign in and verify their email.
- Migration `0035_staff_intake_identity_override.sql`. Clear Valkey `perm:*` after deploy.
