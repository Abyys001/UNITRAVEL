# ADR-0029 · Visa eligibility and travel document checker

Status: accepted (owner brief of 2 Nov 2026, "Smart Visa & Travel Document Eligibility Checker"). Extends ADR-0015 (the VISA service request stays as it is). Adds an approved stack item: the Anthropic API (Claude) as an extraction step, configured write-only in the Developer Panel.

## Context

`/visa` was a request form (destination, purpose, date, travellers) that sent a VISA service request to staff. The owner wants the site to tell a traveller, before they ask for help, what the destination requires **for the exact travel document they hold**, with official sources, and to keep a staff-managed requirements database.

OBSERVED 2 Nov 2026: every GOV.UK foreign travel advice "Entry requirements" page (content API `https://www.gov.uk/api/content/foreign-travel-advice/<country>`) opens with "This information is for people travelling on a full 'British citizen' passport". GOV.UK therefore says nothing reliable about BN(O), BOTC, BOC, British subject, British protected person passports, Refugee Travel Documents, Certificates of Travel or Stateless Person documents, and nothing about non-British passports. Those answers have to come from the destination's own sources, and are often not published at all.

Visa rules change often, and a wrong "no visa needed" can strand a traveller. Immigration advice in the UK is regulated (O6, counsel); this feature gives source-cited information about **other countries'** entry rules and says so. It is not advice about UK immigration.

## Decision

1. **Separate facts.** A check has: travel document type, document issuing country, nationality (citizenship, optional and never inferred), country of residence and residence permit (optional, only a possible condition), destination, transit countries (each with "stays airside" / "changes airport" / "leaves transit zone"), dates and purpose. Residence never changes the document type, and a UK-issued document never borrows British-citizen rules.
2. **Document types are data** (`travel_document_types`), seeded with the nine types the brief lists plus British Overseas Citizen and British Subject passports. Each type has a `ruleKey`: the lookup key for rules. `GB_CITIZEN_PASSPORT` is the only type GOV.UK speaks for.
3. **Requirements database** (`visa_rules`), one row per destination × document type × issuing country (× nationality for national passports) × purpose class (`VISIT` or `TRANSIT`). Status is one of `VISA_FREE, EVISA, ETA, VISA_ON_ARRIVAL, VISA_REQUIRED, TRANSIT_VISA, SPECIAL_PERMISSION, NOT_ACCEPTED, UNCONFIRMED`; every other fact (maximum stay, entries, passport validity, blank pages, document accepted, online application, embassy appointment, fee, processing time, conditions, application link) is a nullable field, and `null` means UNKNOWN and is shown as "not confirmed". Rows carry `verification` (`VERIFIED`, `UNVERIFIED`, `CONFLICT`, `OVERRIDDEN`), `verifiedAt`, `expiresAt` and the evidence list.
4. **Evidence, not opinions.** Each piece of evidence stores the source URL, title, tier (1 GOV.UK FTA, 2 destination immigration authority, 3 official visa / eVisa / ETA portal, 4 embassy or consulate, 5 other government, 6 IATA, 7 third party), whether it is official, the fetch time, the page's own update date where it has one, the claimed facts, the document types the text explicitly covers, and **verbatim quotes**. The research engine keeps a claim only when every quote appears in the text it fetched (whitespace-normalised). Claims the model cannot quote are dropped.
5. **The safety gate (`packages/domain/src/visa.ts`, pure and unit-tested).** A researched status other than `UNCONFIRMED` needs at least one official source (tier ≤ 5) whose quoted text covers the exact document type. GOV.UK FTA evidence covers `GB_CITIZEN_PASSPORT` only, whatever the model says. Two official sources that disagree on the status give `CONFLICT` and the customer sees `UNCONFIRMED` (grey) with both sources until staff decide. Third-party sources never decide a status; they are shown as "supporting, not official". `VISA_FREE` additionally needs the quoted text to name the document (or its holder category); "British nationals" is not enough for a BN(O) passport. A staff override (`OVERRIDDEN`) needs a reason and at least one official URL.
6. **Research engine** (`apps/api/src/modules/visa`). A BullMQ job per rule key on the `maintenance` queue, deduplicated by job id. Sources: the GOV.UK content API for the destination, the trusted sources staff listed for that destination and the global ones, and official links the GOV.UK page itself points to (destination government domains, marked "linked from GOV.UK"). Optionally, Claude's web search with results restricted to the trusted domains finds further pages on those official sites. Pages are fetched by the worker (robots.txt honoured, 15 s timeout, 2 MB cap, identified user agent), reduced to text, and sent to Claude (`claude-opus-5-5`, structured output) one request per check with all page texts; the code then verifies quotes and applies the gate. Every run is stored (`visa_research_runs`) with each fetch's status and timing, the model, token use and the error.
7. **No model, no guess.** Without a configured Anthropic key the run ends `NOT_CONFIGURED` and the answer stays `UNCONFIRMED` with the GOV.UK and trusted-source links. Nothing is ever filled in from model memory: the prompt allows facts only from the supplied texts, and code enforces it (point 4).
8. **Caching.** A verified row is served until `expiresAt` (default 14 days, settable per row and as a setting). A stale row is shown with its age and a refresh is queued. A customer may ask for a fresh check (rate-limited per user and rule key); staff can re-run any row. Check results are held in Valkey for an hour so the page can poll; checks are not stored against the customer.
9. **Credential.** The Anthropic key is a provider credential entered in the Developer Panel (write-only, encrypted like flight-provider credentials, rule 6). The provider row `visa-research` has no flight role.
10. **Permissions.** `visa.read` (staff: rules, runs, sources, history; admin, owner, compliance officer) and `visa.write` (edit, verify, override, sources, document types, expiry; admin, owner). Public routes: `GET /v1/visa/document-types`, `POST /v1/visa/checks`, `GET /v1/visa/checks/:id` (rate-limited by IP; fresh-verification requests need sign-in). Every staff change is audited (`visa_rule.*`, `visa_source.*`, `travel_document_type.*`).
11. **Customer page.** `/visa` becomes checker → results → (optional) the existing VISA service request, prefilled. Colours: green VISA_FREE, blue EVISA/ETA (online authorisation), orange VISA_REQUIRED/VISA_ON_ARRIVAL/TRANSIT_VISA/SPECIAL_PERMISSION, red NOT_ACCEPTED, grey UNCONFIRMED/CONFLICT. Every result shows its sources, the date checked, "never a guarantee of entry", "reconfirm before you travel", and the embassy-contact sentence when unconfirmed. English and Persian.

## Consequences

- Coverage starts empty and grows as customers and staff run checks; most non-British-citizen documents will honestly read "could not be independently confirmed" until staff add destination sources or verify rows.
- Model use costs money per uncached check; the rule cache, the per-key job dedupe and the rate limits bound it.
- Fetching public official pages (not scraping listings, no login, no bypass, robots.txt honoured) is within rule 2; IATA Timatic is BLOCKED (paid, contract needed) and is only a source type staff can list.
- Counsel's view on O6 is still owed before the request service is promoted beyond "information only".
