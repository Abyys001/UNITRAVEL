# ADR-0007 · Stripe Embedded Checkout (test mode only) amends D-03

Status: accepted (Phase D, `docs/ADDITIONAL-REQUIREMENTS.md`; owner decisions 1 and 8, 23 Oct 2026). Amends booklet Decision D-03 ("no online payments in v1", ch. 4, ch. 13.7, ch. 23 vendor table). Ch. 35.1 rule 10: this records the deviation before code. Rule 3 (truth model) and rule 4 (authority) are unchanged: payment success never implies a booking, and every decision lives in the backend.

## What changes in D-03
D-03 parked online payment. Owner decision 1: build Stripe Embedded Checkout fully, **test mode only**, behind the existing feature flag `payments.online.enabled` (**off by default**). Offline payment (bank transfer, cash, card terminal, recorded by staff) stays for every customer. Going live is **BLOCKED** on Stripe's written approval and counsel's advice (money transmission, Iran-connected customers, ATOL timing); this ADR does not lift that.

## Decisions

| # | Question | Decision | Why |
|---|---|---|---|
| P1 | Live mode | **Impossible to enable in code.** `ONLINE_PAYMENT_LIVE_ENABLED = false` is a constant in `packages/domain`; the API refuses a live mode request, live credentials and live keys (`sk_live_`, `rk_live_`) with `LIVE_MODE_BLOCKED`, whatever the flag, the approver or the step-up state. A later ADR must change the constant after the two external approvals | Rule 5: no "temporary" bypass; the owner's decision records live as BLOCKED |
| P2 | Mode change workflow | A mode change is a request (`payments.configure`, step-up) that applies only after a different holder of `payments.mode.approve` (owner) approves it with step-up. Both steps re-check P1. Today every live request is refused and audited (`payments.mode_change_refused`); the approval path exists so the later ADR changes one constant, not the workflow | Decision 1 and the cross-cutting audit list |
| P3 | Checkout Session | Server-side, `ui_mode: "embedded_page"` (the value the installed SDK, `stripe` 23, defines; the plan's wording was right), `mode: "payment"`, one line item named after the invoice number. The **amount and currency come from the invoice row**, never from the client. The API returns the session's `client_secret` and the publishable key only; no secret key ever leaves the server | Rule 3; Stripe guidance |
| P4 | One reusable session | At most one OPEN `payment_sessions` row per invoice (partial unique index). A second request retrieves the same session from the provider and returns its `client_secret`; if the provider says it is no longer open the row is closed and a new attempt is created. The Stripe idempotency key is `inv-<invoiceId>-<attempt>` so a retry after a crash returns the same session | Double charge prevention |
| P5 | Expiry | The session expires at `min(invoice.expiresAt, now + 24 h)` (Stripe's maximum). Stripe's minimum is 30 minutes, so an invoice with less than 30 minutes left is not payable online (`ONLINE_PAYMENT_NOT_OFFERED`, reason `EXPIRES_TOO_SOON`); the customer is told to contact Uni Travel. A same-day (PAY_ON_TICKETING) invoice near midnight Europe/London therefore has no online option | Session expiry never later than the invoice's |
| P6 | Webhook | `POST /v1/webhooks/stripe`, declared `@Public` (no session; the signature is the authentication), verifies the signature on the **raw body** (kept by the JSON parser's `verify` hook for this path only) with the per-mode webhook secret. Each event is stored in `stripe_events` keyed by the Stripe event id; a duplicate is a no-op (HTTP 200). A processing failure rolls the effects back, stores the event as FAILED and answers 500 so Stripe retries; a retry of a FAILED event runs again | At-least-once delivery |
| P7 | What creates a payment | Only a verified event (or the reconciliation job reading the provider) creates a `payment_records` row, method `CARD_ONLINE`, status VERIFIED, `recorded_by` null (system), `provider_ref` = the PaymentIntent id (unique), and then moves the invoice to PAID through the Phase C seam (`InvoicesService.markPaid`). The browser's return redirect is **never** proof: the return page reads our database | Rule 3; ADR-0006 C11 |
| P8 | Amount or currency mismatch | If the paid amount or currency differs from the invoice, no payment is recorded as settling it. The event is stored with outcome MISMATCH, the session is marked MISMATCH, and a **compliance case** (trigger POLICY, evidence kind PAYMENT_MISMATCH) opens through `ComplianceService.openCase` for staff to decide (usually a refund). Disputes (`charge.dispute.*`) open the same kind of case; they change no state automatically | Reuse of the existing case mechanism |
| P9 | Payer screening | The payer name (Stripe billing details, else the customer's name) is screened like an offline payer. A hit opens a case but the verified payment is still recorded: the money has already moved and hiding it would break reconciliation | Ch. 27.1; truth model |
| P10 | Refunds | A refund is requested by staff (`payment.refund.request`) for a PAID invoice with a CARD_ONLINE payment. Up to the existing four-eyes threshold (`WORKFLOW.paymentFourEyesThresholdMinor`, `needsSecondVerifier`) the request is approved by its author; above it a **different** staff member with `payment.refund.approve` must approve, with step-up (same rule as `verifyPayment`). Approval submits the refund to Stripe (idempotency key `refund-<id>`). The payment record and invoice change **only when `charge.refunded` arrives** (full refund: payment REFUNDED, invoice `mark_refunded`; partial: `refunded_minor` grows, invoice stays PAID) | Verified events are the only source of truth |
| P11 | Eligibility policy | Stored as compliance data: policy type `ONLINE_PAYMENT` in `compliance_policies` (versioned, proposed by compliance, approved by an owner). Keys: `product:FLIGHT\|CARGO`, `currency:GBP`, `max_minor:<n>`, `customer:<userId>`. Default deny: online payment is offered only if an ALLOW policy covers the product **and** the currency, no BLOCK policy matches any key, and the amount does not exceed an ALLOW `max_minor`. The seed ships ALLOW for both products and GBP, marked `seeded_pending_counsel` | Rule 5: policy is data, not code |
| P12 | FAKE payment adapter | A second adapter implements the same port for local and test only. It refuses to construct when `APP_ENV` or `NODE_ENV` is `production` (mirror of the FAKE flight adapter) and the Developer Panel refuses to select it there. It produces sessions in our database and events signed with a per-process random secret through Stripe's own header format, so a simulated payment travels the same webhook code path. The simulation endpoint (`/v1/dev-sink/payments/...`) exists only when `APP_ENV=local`. No payment can be made without the webhook path | Rule 2 |
| P13 | Credentials | Stored write-only in `vendor_credentials` (migration 0002), vendor `stripe`, environment `test`, envelope-encrypted: `secretKey`, `publishableKey`, `webhookSecret`. They are never returned, logged or audited with values (only key names). Key prefixes are validated (`sk_test_`/`rk_test_`, `pk_test_`, `whsec_`) | Rule 6 |
| P14 | New dependency | `stripe` (official SDK, 23.x), used only by the Stripe adapter and for signature verification and refunds. The existing stack has no Stripe client; hand-rolling the HMAC scheme and API calls would be less safe than the vendor's audited code. It is not imported by `packages/domain` or `packages/engine` | Rule 1 |
| P15 | Reconciliation | A delayed job per session (`ps-<id>--payment.reconcile`, ids without `:`) scheduled shortly after the session's expiry through `TimersService`, rebuilt by its reconcile, plus a `maintenance` repeatable `payments.reconcile` every 10 minutes for OPEN sessions older than 30 minutes. It retrieves the session from the provider and applies the same handler as the webhook (idempotent by `provider_ref`). It runs even when the flag is off, because money may already have moved | Missed webhooks |
| P16 | Permissions | New: `payment.refund.request` (admin, owner), `payment.refund.approve` (admin, owner), `payments.configure` (developer, owner), `payments.mode.approve` (owner). Granted to existing roles by migration 0007 with a `perm_version` bump; after deploy clear Valkey `perm:*` keys. Resending a payment link reuses `commercial_document.issue`; Developer Panel reads reuse `provider.config.read` | Least privilege |
| P17 | Clients | Web: `/billing/[number]/pay` (Stripe Embedded Checkout, or the FAKE form locally) and its return page; the CSP allows `js.stripe.com` (script), `js.stripe.com` and `hooks.stripe.com` frames and `api.stripe.com` connect, nothing else. Mobile (decision 8): the invoice screen opens the same web page in the system browser; the app holds no Stripe key and no Stripe SDK | Decision 8 |
| P18 | Customer notification | Reuses the existing `invoice.issued` templates for a staff "resend payment link" (the email links to the billing page that holds the Pay button). No receipt template is added here; the customer sees the PAID status on the billing page. UNKNOWN: whether a Stripe receipt email should be enabled (processor settings) | Scope |

## Consequences
- Stripe becomes a processor: DPIA vendor table and data categories are updated (card data never touches our systems; we hold session, PaymentIntent and charge ids, amounts and the payer name).
- `payment_records.recorded_by` becomes nullable (system-recorded payments) and gains `invoice_id`, `provider`, `provider_ref`, `refunded_minor`.
- Runbooks: `docs/runbooks/stripe-webhook-failure.md`, `docs/runbooks/refunds.md`.
- BLOCKED until counsel and Stripe answer: live mode, any customer-facing statement about card payments, the eligibility policy for customers resident in or connected to Iran (kept out by default: the policy is default-deny and compliance screening still applies).
