# ADR-0032 · Apify flights on `/flights`, token bootstrap from environment, live aircraft board removed

Status: accepted (owner approval in session unitravel-23, 3 Nov 2026: "yeah yeah do that", accepting the computed warm interval (~52 h with defaults) and removing the token from `.env` after import). Records the owner brief of 3 Nov 2026 ("make the customer /flights page show real bookable-request flight data from Apify"). Amends ADR-0029 (A6, A8) and ADR-0021 (`/flights` note). Supersedes ADR-0027. ADR-0031 (Iran-origin results held for compliance review) stays in force.

The brief asked for this to be written as `0029-apify-google-flights-provider.md`. ADR-0029 already exists (accepted 2 Nov 2026, same actor, same provider id) and is implemented (commit `bb34763`), so this decision is recorded as a new ADR that amends it rather than overwriting it (OBSERVED).

## Context
- ADR-0029 added provider `apify-google-flights` (actor `lergassy/google-flights-scraper`) as the one owner-approved exception to rule 2. The backend is built: adapter, normalisation, cache, single-flight lock, budget pools and ledger, revalidation, Developer Panel metering (OBSERVED, commit `bb34763`).
- ADR-0029 A8 forbids an environment-variable fallback for the token. The owner now wants a default token supplied through the local `.env` (brief, 3 Nov 2026).
- `/flights` shows the adsb.lol live aircraft board (ADR-0027). The owner wants it replaced by flight schedules customers can ask for.
- `listings.warm-flights` runs every 6 hours (OBSERVED, `listings.service.ts:69`). With 10 routes at `maxResults` 10 one warm costs about $0.10, so 6-hourly warming would cost about $12 a month against a $1.50 prewarm pool (INFERRED from ADR-0029 pricing). The budget guard would stop it, but most warms would fail.
- The brief cites booklet D-10 ("no Google services in critical paths"). `grep` finds no D-10 in `docs/booklet.txt` (OBSERVED). The rule is recorded here as the owner stated it, and its booklet location is UNKNOWN. The project's own rule in CLAUDE.md is "no Google services (fonts, maps, reCAPTCHA) on user-facing paths".

## Decisions
| # | Decision |
|---|---|
| B1 | **Token bootstrap (amends ADR-0029 A8).** On API start, if `apify-google-flights` has no stored credential and `APIFY_TOKEN` is set, the API imports it once into the encrypted provider-credential store (the path the Developer Panel uses), enables the provider and writes the audit event `provider.credential.imported_from_env` (last 4 characters only, never the value). After that the stored credential is the source; env is ignored, including when the stored one is later replaced or marked invalid. The token lives only in the gitignored `.env`; `.env.example` has `APIFY_TOKEN=` empty. Deployed hosts may use the same mechanism. Once the import is confirmed, the owner should remove the token from the host's `.env`. |
| B2 | **Developer Panel Apify page.** Write-only key (last 4, rotatedAt, rotatedBy). "Test connection" calls `GET /v2/users/me/limits`, which costs nothing, and shows plan, monthly usage and limit in USD, and cycle dates. Replacing or disabling the key needs step-up and is audited. The help box (en and fa) covers: where to see the full key, updating it, rotating a leaked key, and the spending cap ($5 on the free plan). It links to console.apify.com and is shown read-only to holders of `provider.config.read`. |
| B3 | **Popular-route warming (amends ADR-0029 A6).** One batched run per warm for all configured routes, `maxResults` 10 per route (new metering field `maxResultsPrewarm`), one departure date per route per warm, rotating across the next 14 days. The warm interval comes from the prewarm pool: interval ≥ 30 days ÷ ⌊pool ÷ cost per warm⌋. With the defaults ($1.50 pool, about $0.101 per warm) that is 720 h ÷ 14 warms, rounded up to every 52 hours, so popular-route data can be up to about 2 days old and always shows its age. Default `listings.flightRoutes`: IST→LHR, SAW→LHR, IST→FRA, IST→AMS, IST→CDG, DXB→LHR, VAN→IST, ERZ→IST, EVN→LHR, IKA→IST. |
| B4 | **`/flights` (amends ADR-0021, supersedes ADR-0027).** Search form at the top, then "Popular routes" from `GET /v1/listings/flights`. Each card shows the airline, flight numbers, operating carrier, airports, local times, duration, stops, layovers (long layovers highlighted), aircraft, cabin, "Google Flights data, updated X ago", and "Request this flight". No price, price level, booking token or Google Flights link in the DOM, payload, JS bundle, analytics or logs (ADR-0004, ADR-0029 A5). When nothing is listed or the budget is spent, the page shows the request form. |
| B5 | **Request this flight.** The existing flight request flow (offer snapshot → ITINERARY request), not a parallel one. Warm searches are stored with owner type `SYSTEM` (no person, no contact data, customer projection only), and any caller may read them so a listing card can open its itinerary. Submitting still needs sign-in and the normal ownership of the created request. This is the one exception to the per-customer search ownership check (rule 4), limited to `SYSTEM` searches. Iran-touching requests go to COMPLIANCE_HOLD (ADR-0031 I4). |
| B6 | **Live aircraft board removed.** The `LiveFlights` component, `GET /v1/live-flights`, its contract, the adsb.lol worker poller, en/fa strings and tests are deleted. ADR-0027 is superseded and its DPIA R20 entry is closed. |
| B7 | **Console.** Requests from `/flights` and `/search` show the badge "Source: Apify / Google Flights, fetched …" and, for `pricing.read.internal` only, price, price level and the Google Flights link. "Revalidate now" uses the staff pool. UNKNOWN baggage and conditions are flagged as "record from the booking panel before quoting", and rule 3 still blocks the quote. The dashboard gets an Apify usage card for `provider.config.read`. |
| B8 | **Not changed.** Truth model (ADR-0029 A3), compliance policies (ADR-0031), cache TTL 3 h, single-flight lock, pool split 40/30/30 with a $0.75 staff reserve, CI never calls Apify, and one live smoke run capped at `maxTotalChargeUsd=0.02` after owner approval. The adapter stays behind `FlightSupplierAdapter`, so Duffel or Amadeus can replace it in the Developer Panel. |

## Consequences
- A Google-sourced listing now sits on the customer flights page. The owner accepts that this conflicts with the "no Google services on critical/user-facing paths" rule the owner cited as D-10. Customers' browsers never contact Google: data reaches them only through our API.
- An env-supplied secret exists on disk until the owner removes it after import. This is weaker than ADR-0029 A8 and is accepted for first-boot convenience.
- Popular routes are up to about 2 days old on the free plan. More frequent warming needs a larger prewarm pool, which is configuration only.
- Customers lose the live aircraft view. Nothing else uses `GET /v1/live-flights` (to be confirmed by search before deletion).
