# ADR-0040 · Customer portal redesign: overview, inbox, purchase tracking, live cargo tracking

Status: accepted. Requested by the owner on 21 Nov 2026 (brief "Task 2: Redesign and Complete the UniTravel Customer Portal"). Plan approved the same day with three answers: `/dashboard` is the landing page after sign-in; Flutter is out of this pass (web only); live cargo tracking through TrackingMore. Stage record: `docs/stages/STAGE-31.md`.

ADR-0016 (customer club), ADR-0018 to 0021 (activity, support, assigned services, listings), ADR-0025 (tracking needs sign-in) and ADR-0026 (mobile paused) stay in force. Club points come from Task 1 (ADR-0039, migration 0029); this ADR only reads them.

## Context
- The customer site has no overview. `/requests` acts as the dashboard. Track, club, shipments and the cargo and service detail pages use their own layouts, so only 6 pages share the panel frame. (OBSERVED)
- Content panes are translucent white (`card-brand`, `bg-white/70`) over the pale page background with `#dbe5f2` hairlines. Cards and the page blend together, which is the owner's readability complaint. Pages use raw palette classes rather than the semantic tokens. (OBSERVED)
- The inbox can mark all as read, but has no detail view, no "important" filter and no unread count for the header. Support tickets have no read state, so a staff reply is easy to miss. (OBSERVED)
- Cargo tracking events are entered by staff only. `CargoTrackingPort` and the `PARTNER_API` source exist, but nothing implements them. (OBSERVED)
- TrackingMore documents an air waybill tracking API with webhooks and carrier detection from the AWB prefix, covering about 116 airlines. (DOCUMENTED, trackingmore.com; endpoint details read from its API reference at build time)

## Decisions

| # | Decision |
|---|---|
| D1 | **One overview endpoint.** `GET /v1/me/overview` (`flight_request.read.own`). It is built from the existing services, and every part of it is filtered to the signed-in customer: active and previous requests (flight, cargo, service), pending actions, purchases (paid invoices, issued tickets), unread inbox and support counts, the latest notifications, open support tickets, a club summary, account completeness and the travel card state. Strict Zod schema `PortalOverview`, which is added to the serialiser property test. |
| D2 | **Inbox.** `GET /v1/notifications` gains `filter=all\|unread\|important` (important = `critical`) and cursor paging. `GET /v1/me/unread` returns `{ inbox, support }` for header badges. Single-message read already exists (`MarkReadBody.ids`). The web inbox is a list with a detail pane on wide screens and a list with a detail page on phones. A message links to its request through `data.ref`. |
| D3 | **Support read state.** Migration 0031 adds `support_tickets.customer_read_at`. Opening the ticket marks it read. A staff reply leaves it unread for the customer and sends `support.reply` to the inbox (en/fa templates). `CustomerTicketSummary` gains `unread`. |
| D4 | **Track a purchase.** `GET /v1/track/:ref` gives a customer-owned detail with: a progress bar of named steps (done, current, upcoming), a history of what happened, the next expected step written out, and the documents (quotation, invoice, tickets). Search accepts a reference or, for cargo, the AWB. Any other customer's reference returns 404. |
| D5 | **Live cargo tracking through TrackingMore.** A `TrackingMoreAdapter` implements `CargoTrackingPort` (source `PARTNER_API`). The key is write-only in the Developer Panel, following the existing credential pattern. The adapter is off until a key is saved, and off on deployed hosts until TrackingMore is listed as a processor in the DPIA. When staff record an AWB, it is looked up at TrackingMore (`POST /v4/awb`, `Tracking-Api-Key` header). Updates then come from a worker poll every 30 minutes (up to 40 shipments per run), and staff can trigger a refresh. The webhook receiver is BLOCKED: TrackingMore's web docs refuse automated clients and the official SDKs do not document the signature scheme, so no unsigned endpoint is exposed. Updates go through the existing ingest path: `externalEventId` dedupe, append-only, and staff corrections still win. Only `delivered` maps to one of our event codes. Every other checkpoint is stored as a NOTE with the provider's own text and shown to the customer that way; it is never guessed. Checkpoint times are read as UTC (UNKNOWN whether the provider sends a time zone), and a checkpoint without a usable date is dropped. Switching it on needs `dpiaApproved` on deployed hosts. The customer view states the source of each event (our cargo team or the airline via TrackingMore) and the connection state (`NOT_CONFIGURED`, `PENDING`, `ACTIVE` or `UNAVAILABLE`). When it is not active, the page says live carrier tracking is not connected. No tracking data is ever made up. |
| D6 | **Club.** The portal shows: membership status, tier, benefits, credit balance, and points balance and history. The points fields come from `CustomerClubView.points` (Task 1); until they exist, the points tile is not shown. The customer API stays read-only. Only staff with the club permissions can add members or change points. |
| D7 | **Travel card.** The overview carries `travelCard.status` (`COMING_SOON` today, from the `card` site flag). The dashboard tile is a component with two states. Today it shows only the "Coming soon" state and copy, with no actions. Turning the card on changes that tile, not the dashboard layout. |
| D8 | **Portal shell and surfaces.** One `PortalShell` for every signed-in customer page: dashboard, requests, inbox, track, shipments, club, support, billing, tickets and account. It has a sticky top bar with inbox and support badges, a section nav (side rail at 1024 px and wider, a scrolling tab bar below that), and solid content. Content cards are opaque white (`--surface-raised`) with a `--rule-strong` border and `--shadow-card` on the cloud page. Text uses `--ink` and `--ink-muted` only, at 4.5:1 or better. Glass stays on the dark brand band, per the surface rule in DESIGN.md. The duplicate `--ink` token is resolved in `tokens.json`. URLs do not change, and sign-in lands on `/[locale]/dashboard`. |
| D9 | **Out of scope.** Flutter screens: mobile stays paused under ADR-0026 and follows in a later pass, reusing these contracts. Points earning. Payment flows, which stay as they are. |

## Consequences
- TrackingMore is a new processor: it receives AWB numbers, airline and route only, with no customer names or contact details. A DPIA row and a counsel or owner sign-off are required before it is enabled on a deployed host. (BLOCKED until then)
- Monthly cost depends on the TrackingMore plan; the owner holds the account (UNKNOWN).
- Customer pages lose the glass-on-content look from the 2026-10-29 update. The owner's readability request takes precedence, and DESIGN.md records the change.
