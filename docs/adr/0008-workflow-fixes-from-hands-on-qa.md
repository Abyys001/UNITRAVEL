# ADR-0008 · Workflow fixes from hands-on QA (command guards, cargo payments, tracking, passenger mix, fee facts)

Status: accepted (24 Oct 2026, owner QA round). Extends ADR-0003 (state-machine interpretations). Ch. 35.1 rule 10: each item below interprets the booklet where it is silent or ambiguous.

| # | Question | Decision | Basis |
|---|---|---|---|
| W1 | Dialog commands were always disabled in the action list | A transition has `guard` (facts about the request: shown as the disabled reason) and `inputGuard` (what the actor types in the dialog). `allowedCommands` evaluates only `guard`; `execute`/`evaluate` evaluates both. State reasons (travellers not VERIFIED, payment not PAID) stay visible | Ch. 15.1 "Commands, not fields": the server tells the console what is possible and why not; a dialog's own fields cannot be known before it opens |
| W2 | Cargo payment | Offline payments for CARGO use the flight path: `payment_records` with `request_type = CARGO`, payer screening, four-eyes above `paymentFourEyesThresholdMinor`, status computed from verified records against the accepted cargo quote total, then `settleFromPayments` for the invoice. Allowed from `ACCEPTED` onward (not in terminal exits). **No ATOL gate**: ATOL (ch. 27.6) concerns flight packages, not freight. INFERRED: the booklet's payment row (13.7) is written for flights; the cargo chapter (14) only says COMPLETED is "closed after delivery and settlement". Counsel to confirm no cargo-specific timing rule | Ch. 13.7, 14.5, 27.6 |
| W3 | Cargo compliance four-eyes | A cargo case sets `requiresFourEyes` when a party screening returns `MATCH` (strong), matching the flight rule (blocked carrier) in spirit | Ch. 15.7, risk R-01 |
| W4 | Cargo tracking vs request state | A staff-entered tracking event needs the request to have reached the event's stage (`trackingEventAllowed`): before BOOKED only `NOTE`; `PICKED_UP`, `HELD`, `DAMAGED` from BOOKED; `RECEIVED` from AWAITING_HANDOVER; `DEPARTED` from RECEIVED; `ARRIVED`/`AT_CUSTOMS`/`CLEARED`/`OUT_FOR_DELIVERY`/`RETURNED` from IN_TRANSIT; `DELIVERED` from OUT_FOR_DELIVERY. In EXCEPTION the stage is the state it will resume to. Payment status is **not** a precondition: the booklet makes no cargo payment gate before pickup (UNKNOWN; see W2) | Ch. 14.5 (events mirror fulfilment), 14.8 |
| W5 | Policy proposals could not be rejected | Add `reject` (approver/owner, reason required) and `withdraw` (the proposer) to the policy approval workflow. Both end the proposal without changing the policy; nothing is ever auto-approved | Ch. 27, rule 5 (policies are data changed with approvals) |
| W6 | Travellers vs searched passengers | At submit the API requires the per-type count of `travellers[].passengerType` to equal the search/manual query's `passengers` (error `VALIDATION_FAILED`, path `travellers`, code `PASSENGER_MIX_MISMATCH`). Re-pricing after submit was rejected: the offer snapshot is priced for the searched mix, and the customer never sees a price (ADR-0004), so the only honest fix is not to accept a different mix | Ch. 12.4 (mix validated server-side before pricing), 13.6 |
| W7 | Fee-type change/refund facts | A quote option condition that is allowed with a penalty needs `penalty.amountMinor > 0`; a blank/zero fee is `conditions.<change|refund>.penalty` in `unknownQuoteFields`, which blocks `send_quote` (rule 3: never infer conditions) | Ch. 12.5, 15.5 |
| W8 | "Record payment" offered when it will fail | The staff detail carries `paymentRecording { allowed, reason?, suggestedAmount }`. Under PAY_ON_TICKETING it is allowed only once tickets exist; the amount is pre-filled with the outstanding total of the accepted option / cargo quote | Ch. 13.7, 27.6 |
